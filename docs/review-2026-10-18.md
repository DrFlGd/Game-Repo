# Review of v0.5.18 (2026-10-18)

Jerred asked for the last build to be made "air tight" before any new features. This is
the review of v0.5.18 (main at dbd9950) and the findings it made. The plan that fixes
them is in [PLAN.md, "Hardening after the v0.5.18 review"](PLAN.md#hardening-after-the-v0518-review-d78d82),
which says which batch each finding belongs to and what has been done. The shared copy
Jerred read is the Claude Doc "Game Repo v0.5.18 review"; this file is the one to work
from.

**Verdict:** not air tight. The everyday workflows work end to end. In the run-through, the
audit counts matched the fixture's expected audit exactly, originals were untouched to
the byte, inode and time, and an interrupted change finished cleanly. But five findings
(C1 to C5) can lose files, all in Undo or in a step that writes over a file.

## How it was reviewed

Eight reviews ran side by side, each on one part of the app, on synthetic data only:

1. The interface in Chromium against `gamerepo-cli serve` with `tests/tauri_shim.js`: every
   page, menu entry, Settings section and dialog, at 1280×800 and at 720 px.
2. The front-end code against `api.rs`: all 188 `api()` calls (every command and argument
   matched), state and effects, errors, wording.
3. Scanning, hashing, archives and disc images, DATs, audit, arcade, the index.
4. Organise, Convert, Import from folders, Add a game, BIOS gather, the journal and Undo.
5. Collections, history, exports and layouts, add-ons, documents, magazines.
6. Metadata, scraping, sources, Identify, Steam, LaunchBox, the Library index, the job
   system and the Tauri shell.
7. The workflows end to end through the same calls the page makes, with the files checked
   on disk afterwards.
8. Tests, CI, and drift between this plan's decisions and the code.

"Reproduced" means it was made to happen on synthetic data; "traced" means it was
followed through the code only. File and line numbers are as of dbd9950.

Severity: **Critical** loses or corrupts files, or crashes on a common path. **High** gives
a wrong result in a realistic case. **Medium** is an edge case or notably slow on large
sets. **Low** is polish and wording.

## Critical

**C1. Undo deletes a change's output before checking the original can come back.**
organise.rs:1996-2016 (`undo`, the `_` branch "a file the change wrote") calls
`remove_file(to)` and only then finds "its set-aside copy is gone". If
`.gamerepo-set-aside` was deleted by hand, or a USB drive came back under another letter,
both the new file and the original are lost, and the change is logged as undone so it
can't be retried. Reproduced: zip in place, delete the set-aside folder, Undo: `undone 0`,
two problems, both ZIPs gone. *Fix:* check every held file exists before touching `to`;
set `to` aside instead of deleting it; don't log "undone" while there are problems.

**C2. Undo deletes a file the user replaced after the change ran.** organise.rs:1997
removes `to` without checking it is still the file the step wrote. Reproduced: import a
game (copy), replace the file with other content, Undo: the file is gone, not set aside,
no problem reported. *Fix:* record each written file's size and modified time (or SHA1)
in the journal; compare before removing; set aside or report a file that differs.

**C3. Copy and link steps overwrite a file that appears at the target after the
preview.** organise.rs:1606-1613: when `hard_link` fails because the target exists, it
falls back to `copy_checked`, whose `fs::rename(tmp, to)` (organise.rs:1538) replaces the
file. Extract does the same (organise.rs:1631). Plans stay pending for a day, and the
same `perform` code serves Organise copy, Import, export and Update. Reproduced twice
(plan, then write the user's own file at the target, then Run: `done 1, failed []`, the
file holds the ROM; Undo then deletes it). Move steps refuse correctly ("is there
already"). *Fix:* refuse when `to` exists in link, copy and extract and in `copy_checked`
before the final rename, as the zip, text and cue steps already do.

**C4. A game that fails to extract or re-zip still has its archive set aside.**
organise.rs:982 builds the consumed-archive `aside` step with `game: String::new()`, and
`run` skips the rest of a failed game only when its game name isn't empty
(organise.rs:1864). In Extract, Rename where they are with loose files, or rebuilding a
7z as a ZIP, the source archive leaves its folder even though its game failed, and the
next Empty deletes it. Reproduced: `organise gb --mode rename --format loose` with a
damaged member: "1 of 2 steps done", the only copy left in `.gamerepo-set-aside`. *Fix:*
tag each consumed-archive step with the games it serves and skip it when any failed.

**C5. Export Update sets aside the card's copy of a game still in the collection.**
export.rs:725-735: `wanted` holds only games the library can place now, so a game whose
library file is missing, or whose drive is unplugged (scan.rs:362 marks the whole root
missing), has its card copy set aside. That copy may be the only one left; Empty deletes
it. Reproduced with Knulli: Pac-Man moved out of the library, rescanned, `export update
--dry-run` planned `aside roms/gb/Pac-Man (USA).gb` while the collection listed it as
missing. *Fix:* set aside only recorded files whose game is no longer among the
collection's games.

## High

**H1. Undo removes the folders with games it imported into, and every empty folder above
them.** organise.rs:2025-2036: `made` holds the parent of every written file, not the
folders the change created; with `plan.out` unset (several places) the climb has no
stop, and `starts_with(out)` lets the root itself go. Reproduced: empty roots
`Drive/Games/Roms/GB` and `…/GBA`, one game imported into each, Undo: GB, GBA, Roms,
Games and Drive deleted, both roots `found: false`, the next import went to
`Library/Game Boy`. *Fix:* record the folders `make_parent` creates; never remove a
folder with games or anything above one.

**H2. An unreadable library.json is treated as empty and the next write wipes it.**
library.rs:186 `meta()` uses config.rs:152 `read_json_object`, which returns `{}` on any
read or parse error; `update_meta` (library.rs:199) then writes only its patch. One typo
in a hand edit, or a moment when a sync tool or antivirus holds the file, and the next
settings change loses the id, the folders with games, systems and naming. config.json
behaves the same. Reproduced (`,,` added, `roots add`: the file held only the new root,
`id: null`). *Fix:* tell "missing" from "unreadable"; refuse to write over an unreadable
file and name the line that's wrong.

**H3. Rename these can't fix a ZIP whose name is right but whose file inside is
misnamed.** organise.rs:844: `zip_op` targets `<base>.zip`, the source itself, so the
check at :936 records it as a conflict (:941): "1 in the way (left as they are)", for
ever. Common in older sets (`Game (World).zip` holding `game (w) [!].gb`). Reproduced.
*Fix:* when the target is the source archive, write the new ZIP beside it, set the
original aside, then rename.

**H4. On Windows, copying into the files' own folder replaces an original that differs
only in case, and Undo deletes it.** Traced: `place` (organise.rs:656) and `same_file`
(:936) keep a case-only difference, `hard_link` fails, `copy_checked` replaces the
original, Undo's `remove_file(to)` (:1998) deletes the only copy. *Fix:* skip steps whose
target is the same file as the source; never remove such a target on Undo.

**H5. A renamed cue/bin disc is imported without its cue.** `subset::review` matches only
the tracks; the sheet goes to "files no DAT knows" with no system. After the import the
folder has the bins and no cue, the audit shows the game partly there, and Rename these
plans nothing. Reproduced (flows `flow4e.py`). *Fix:* attach any sheet beside matched
tracks whose FILE lines name them (`cue::file_names`, as the scan does), and give a disc
game a folder of its own.

**H6. Importing a good copy of a game the library holds as a bad dump does nothing.** The
review lists the game as matched, the preview's *Left alone* says "There's a file called
Gamma (Japan).gb … already", and the window says "Nothing to import: the library has them
all"; the audit still shows a bad dump. A first import said "5 games to bring in" and
brought in 4 without saying why. Seen in the browser. *Fix:* offer to replace a file that
doesn't match the DAT, setting the old one aside; never say "has them all" when anything
was left alone.

**H7. Headered ROMs inside ZIPs never match with the default quick scan.** archive.rs:108
(`Hashes::quick` has no headerless hashes); audit.rs:18-31 needs `hl_crc32`. Zipped NES,
FDS, Atari 7800, Lynx, SNES copier dumps and `.v64`/`.n64` show as missing and as bad
dumps against No-Intro's headerless DATs, libretro's starter DATs included. Reproduced:
quick scan "1 of 2, 1 bad dumps", full scan "2 of 2". *Fix:* in quick mode read members
in full when their extension can carry a header (nes, fds, a78, lnx, sfc, smc, swc, fig,
v64, n64); they are small.

**H8. Any error reading an archive makes it a plain file for good.** scan.rs:240-243 falls
back to hashing it as a file (`kind='file'`, `hashed=2`), its members leave the audit and
no later scan looks inside again. Triggers: (a) every RAR reader shares one scratch file,
`temp/gamerepo-rar-<pid>/member` (archive.rs:221-223, 247-272, 325-349), so two readers
(the default) clobber each other and one RAR can be credited with another's hashes (CBR
pages read in parallel by magazines.rs too); reproduced: 40 RARs, two readers, 14 became
plain files; (b) one member with a bad CRC hides the good ones; (c) bzip2 and LZMA ZIP
members (the `zip` crate is built with deflate only). *Fix:* a scratch path per call;
fall back to a plain file only when the container can't be opened; record a bad member
as unreadable and keep the rest; treat I/O errors as failed so the next scan retries;
enable the zip crate's `bzip2`, `lzma` and `deflate64` features.

**H9. A scan holds the index's write lock across 250 hashed files.** scan.rs:503-529
commits by count only (`BATCH=250`). With disc images nothing is committed for a long
time, a crash loses it all, and every other writer (`audit::summary`'s cache,
`browse::refresh`, DAT import, edits) fails after 5 s with "database is locked".
Reproduced (ten 1 GB files: "0 of 10 committed" at 12 s, a write failed after 5.0 s). If
`record()` fails the readers keep hashing the queue. *Fix:* commit at 250 files or about
a second, whichever comes first; stop the readers on error.

**H10. A CSO with a damaged header crashes the whole app, on every scan.** image.rs:695-697
allocates `vec![0u8; (blocks+1)*4]` from the header's own total. Reproduced: a header
claiming 2^49 bytes aborts with "memory allocation … failed" (exit 134); the file stays
`hashed=0`, so every scan crashes again. Suspected, same family: a CHD with
`hunk_bytes=0` divides by zero (image.rs:256), a GDI with sector 0 (image.rs:491). *Fix:*
check sizes against the file's length before allocating or dividing.

**H11. A correct non-merged arcade set lists every shared ROM as a duplicate.**
audit.rs:214-215 (`DUPLICATES` has no arcade case). Reproduced: parent and two clones,
non-merged: "6 matched … 9 duplicates". A real MAME set would show tens of thousands.
*Fix:* for arcade DATs, a file is a duplicate only when it isn't at one of its ROMs'
`dat_places` positions while another file is.

**H12. Matching by name crosses systems in collections.** collection.rs:705 and :816:
`Sources.names` is one set for every system. Reproduced: a DAT with Game Boy Tetris and
NES Pac-Man made a collection of four games. Affects collections from folders and from a
DAT. *Fix:* key names and hashes by system.

**H13. Tagged add-ons in the audit DAT become games of their own in collections.**
collection.rs:818 (compare browse.rs:200). "Alpha (USA) (DLC)" counts as a game and as
Alpha's add-on: the export plan has two links to one target, the DLC gets its own
playlist, gamelist and Pegasus entries, pictures are written twice. Reproduced. *Fix:*
skip `addons::kind_of(name, false)` rows unless the DAT is an add-on DAT.

**H14. RetroArch and LaunchBox point multi-file disc games at a folder.** export.rs:480
(`esde: style != "naming"`) and :783: every layout but Plain folder puts a cue/bin game in
a folder named `Game (USA).cue/`, and the playlist `path` and LaunchBox `ApplicationPath`
name that folder. Reproduced. Suspected the same for Pegasus, whose `extensions` would
also make every `.bin` a game. *Fix:* list paths outside es-xml name the sheet inside the
folder, or these layouts keep disc files loose.

**H15. Gamelist entries a device wrote are duplicated on Update.** export.rs:935:
`find("<game>").or_else(find("<game "))` falls back only when no plain `<game>` exists, so
once Game Repo has written plain entries, Knulli or Batocera's `<game id=… source=…>`
entries are skipped, duplicates are added, and theirs never refresh. Reproduced. *Fix:*
take the earlier of the two matches each pass.

**H16. Export these… after a search and Ctrl+A exports every game in the system.**
collections.js:826 turns "all" into `<system>/*`, ignoring the search. Reproduced in the
browser: the dialog said "Export 1 game", the preview "3 games to export". *Fix:* with a
search active, turn "all" into the matching keys (`browse_keys` with the search).

**H17. A scrape can run beside a metadata change, and Undo then strands data.**
api.rs:1132 (`scrape_run` never calls `begin_change`), api.rs:295; scrape.rs:253/331 read
`game.json`, fetch pictures, then write back. Delete metadata… or Rename folders… is
accepted while a scrape runs; the scrape writes into folders being set aside; Undo
returns `undone: 2, problems: []` but older answers stay in `.gamerepo-set-aside`, and
Empty deletes them. A hand edit made while that game is scraped is lost. The same gap
exists for Make details again (`remake_all`), Identify's retitle (renames `PC/…`
folders) and `browse_edit`. Reproduced. *Fix:* treat a scrape, `remake_all` and
Identify as changes, or add a metadata-writer lock, and refuse edits and changes while
it's held.

**H18. Identify… on a DAT game keeps the wrong game's details.** scrape.rs:459 (`pick` →
`apply` → `sources::make` with `Rules::of(lib)`), sources.rs:172 (`ranked`). The pictures
switch over; the description, year and title stay with the source ranked first. PC
games get it right (`pcmeta::rules`, `identified_by` first, pcmeta.rs:87). Reproduced.
*Fix:* record `identified_by` on DAT games and rank it first.

**H19. Name-only scrape answers aren't limited to the system for 18 systems and every
system added by hand.** scrapers.rs:67 (`SYSTEM_IDS`), `igdb_search` :741, `tgdb_search`
:851, scrape.rs:176-199 (the first result with the same title is accepted). No IGDB id
for xbox, colecovision, intellivision, vectrex, wonderswan, wonderswancolor, 3do,
atari5200, atari7800, atarijaguar, atarijaguarcd, fds, sg-1000, ngp, neogeocd, pcfx,
cdimono1, pokemini; TheGamesDB lacks 14 of them. Reproduced: `scrape colecovision`
sent no platform clause and reported "1 found". *Fix:* without a platform id, keep
results as candidates rather than accepting one (or check the platform name); fill in the
missing ids.

**H20. Importing after renaming a magazine replaces its list of issues.**
magazines.rs:306-310 finds a magazine by title only; after *Retro Mag* is renamed, an
import of "Retro Mag 003" writes a new, empty `magazine.json` in the same folder.
Reproduced (2 issues became 1; the old ones are on disk but listed nowhere). *Fix:* load
the manifest the target folder already has.

**H21. One magazine with a multibyte name stops the whole read.** magazines.rs:146:
`t.split_at(t.len()-4)` cuts by bytes. Reproduced: "週刊ファミ通 0123 (1995-01).pdf" fails
with "end byte index 14 is not a char boundary". *Fix:* split by characters.

**H22. The Audit command bar runs off the right edge between 1000 and 1300 px.**
styles.css:1210 `.bar-place { flex: 0 0.01 auto }` hardly shrinks, so Scan and ⋯ (and on
NES, Organise and Convert) go off-screen, the page scrolls sideways and stays shifted.
Seen in the browser at 1000, 1280 and 1300 px. *Fix:* `flex: 0 1 auto` with an ellipsis
on `.page-count`, or let the bar wrap.

**H23. Metadata is stuck on "To start" when the remembered system has no DAT.**
metadata.js:335, 347, 372-373, 395: `audit_summary {platform}` for a system with no DAT
returns `{"summary":null,"platforms":[]}`, so the ribbon is empty and nothing can be
picked (another library opened, or the DAT removed). Reproduced. Audit has the same cause
(audit.js:137) but keeps its ribbon. *Fix:* when `summary` is null ask again with no
system and clear the preference, or always return `platforms`.

**H24. Every CI job can push to main and publish releases, and runs unpinned code.**
desktop.yml:29-30 `permissions: contents: write` for the whole workflow; checkout keeps
the token; the same jobs run `cargo install --git …/msedgedriver-tool` at its newest
commit (:201), `tauri-driver` with no version (:200), `npx @tauri-apps/cli@2` (:188),
`pip install` unpinned, and actions pinned only by tag. *Fix:* read-only by default, write
only in the release and report jobs, `persist-credentials: false`, pin to SHAs and exact
versions.
