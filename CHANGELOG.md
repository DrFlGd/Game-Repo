## For agents

### What this is

A Windows desktop app (Tauri 2) for organising large video game collections: auditing ROM sets against DAT files, building and exporting collections (ES-DE, Steam), importing PC games into a common layout, and scraping each game's details, media and manuals, with the user's own documents attached. The owner ("DrFlGd", Jerred) steers by phases; the plan, every decision taken (D1–D18, D21–D24, D29–D30, D36, D40; D31 proposed; D19–D20, D25–D28, D32–D35, D37–D39 and D41 proposed and followed) and the phases are in `docs/PLAN.md`.

The code started as a trimmed copy of [Model Library](https://github.com/DrFlGd/Model-Library) (same owner, same stack): its Tauri shell, its one-command-table backend, its library folder, its jobs and its Preact interface. Much more of it is meant to come across as the phases need it (the browser views, the sorting workspace for the PC inbox, journals and Undo, ZIP/7z reading, the side viewer for documents): look there before writing something from scratch. `docs/PLAN.md` section 5 lists what carries over.

### Conventions

- **Phases and releases.** The repository keeps `0.<phase>.0` in `desktop/src-tauri/tauri.conf.json` and `desktop/Cargo.toml` (`tools/set_version.py 0.1.0` stamps them; bump it when a phase starts). CI picks the next free `0.<phase>.<n>` from the release tags and publishes `v<version>` from `main` only when the Windows app, the Rust tests and both acceptance tests pass. The release notes are the **Unreleased** section below, so write it for the user.
- **Windows only for now** (D3). Keep code portable all the same; the Linux build runs only from *Run workflow* with "Linux too" ticked.
- **Plan first.** For a new phase or a big feature, write the design into `docs/PLAN.md` before code ("Phase N design"), and afterwards a "Phase N notes" section recording what was built and where it differs.
- **Performance on large sets** is the first requirement (D1): hundreds of thousands of files. Put lookups and joins in SQLite with indexes, stream rather than load, hash each file once and remember it by size and modified time, and run anything long as a job with progress and Stop.
- **The library folder is the source of truth** and must make sense without the app. Never write a database into it (the index is per computer and rebuilt from the files and DATs); keep unknown keys when rewriting its JSON; write JSON with `config::write_json` (sorted keys).
- **The index's schema** grows by appending steps to `index::MIGRATIONS`; a step that has shipped is never edited. An index from a newer app, or another library's, is set aside as `<id>.old.sqlite` and made again.
- **Originals are never touched by default** (D5): renaming in place and moving into the library are explicit, journalled choices with Undo.
- **Scraped data, media and documents are keyed by game id** (ROM hash → game; PC games by their own id), never by file name (D13).
- **External tools** (dolphin-tool, innoextract) are found in the app's `tools/` folder, on PATH or at a path set in Settings › Tools; nothing is downloaded (D14). Prefer doing it in the core: CHD, CSO and ZSO are written by the app.
- **Text:** plain words, no jargon in the interface; British spellings in the UI (organise, colour), as in Model Library.
- **Tests grow with each phase.** Add checks to `desktop_page.py` for every user-visible feature, Rust tests for the core, and `desktop_ui.py` when it needs the real app. Never commit real ROMs or DATs; make synthetic ones.
- **Commits:** a subject saying what changed for the user, a body with the details. Add a line under **Unreleased** for every user-visible change.

### Working in a cloud session

- **Rust:** crates.io was reachable on 16 October 2026 and the whole workspace resolved online (`Cargo.lock` is committed). If it's blocked, `vendor.yml` pushes `gamerepo-core`'s dependencies to the `crates-vendor` branch whenever `desktop/core/Cargo.toml` changes: build offline from it with a workspace holding only `core` and `cargo <cmd> --offline --config <branch>/vendor-config.toml`.
- **Build and test only the core locally:** `cd desktop && cargo test -p gamerepo-core && cargo build --release -p gamerepo-core`. The timing checks are ignored by default: `cargo test --release -p gamerepo-core -- --ignored timing --nocapture --test-threads=1` (CI runs them, one at a time so each is timed alone).
- **Try the CLI on synthetic data:** `python3 tests/fixtures/make_fixtures.py <dir>`, then `gamerepo-cli roots add <dir>/Roms --home <h> --library <lib>`, `scan`, `dat import <dir>/dats/gb.dat`, `audit gb` with the same `--home`/`--library`. The Tauri app needs WebView libraries the session doesn't have; it builds only in CI.
- **Acceptance test locally:** `python3 tools/build_desktop.py --out build/desktop`, then `python3 tests/desktop_page.py --cli desktop/target/release/gamerepo-cli --ui build/desktop/ui --home <tmp> --out <shots> --chromium /opt/pw-browsers/chromium` (`pip install playwright`; use the pre-installed Chromium, don't download one).
- **GitHub from the session:** GraphQL may be blocked, so open PRs through the REST API (`gh api repos/DrFlGd/Game-Repo/pulls --method POST`). CI reports land on the `desktop-ci-windows` branch (logs, acceptance screenshots in `page/`); fetch it to read results.

### Known limitations now

- RAR is read, never written; 7z is read and not written yet.
- Exports keep the library's format (Convert first); no `.m3u` for multi-disc games.
- The device layouts follow each firmware's documentation as of October 2026 and haven't been tried on a device: Knulli's and ROCKNIX's picture names follow Batocera's scraper (`images/<game>-thumb.png`), muOS's catalogue names beyond Game Boy and SNES, and Batocera's folder names for some systems, are to check against real cards. Each can be put right in a copy of the layout.
- Scraping: ScreenScraper, IGDB and TheGamesDB were written from their documentation and other clients' code (ES-DE, Skyscraper, RomM) and tested against stand-ins only, since the build sessions can't reach them; ScreenScraper needs the app's own developer id and password, which Game Repo doesn't have yet. A game's folder keeps its name when a new DAT renames the game (Phase 6). Text is read from PDFs that have it, not from scans. Scrape… on the page covers a system's games or its whole DAT; a collection's games are scraped from the command line (`scrape <system> --collection <id>`).
- ZIPs the app writes are at most 4 GB a file and 65,535 files (no ZIP64), plenty for cartridge games.
- Only the newest change can be undone (then the one before it, and so on); emptying what a change set aside ends its Undo.
- Renamed files are read again on the next scan (a move to another folder keeps its hashes; the rename can't be told apart from a different file safely).
- DATs whose platform isn't in `platforms.rs` or the library's systems (TOSEC's names, for one) are asked about once per DAT name; the answer is kept in library.json.
- A DAT ROM with no CRC32 isn't matched (every Logiqx and ClrMamePro DAT seen so far gives one).
- Two skins (Drafting Sheet, the default, and Classic). Model Library's Parts Bin and Layer Line were 3D-printing themed and weren't brought across.
- `web/styles.css` still holds Model Library's rules for views not built here yet (the browser grid, the workspace, the inspector); they're kept for the phases that bring those views, and pruned once those pages exist.
- Installers aren't code-signed, and there's no auto-update.
- PC games: installers are never run (Unpack, or point the game at where it's installed); Steam's and GOG's answers were checked against their live shapes but the app has only been tested against stand-ins; LaunchBox's database is about 100 MB to fetch. Steam's hashed artwork paths come from its store browse service, with the fixed names as the fallback.

## Unreleased

- **Export to an SD card**: Export… now goes to a *layout*: ES-DE, ES-DE on Android or Linux, muOS, Knulli, ROCKNIX or a plain folder. Choose the card (or folder) and the games go into each system's folder as that firmware names it, with its gamelists (ES-DE, Knulli, ROCKNIX) or muOS's catalogue of box art, previews and descriptions, pictures made a handheld's size, manuals, and BIOS files. A system the device doesn't have is left out and said so. Update and Check follow the layout the export was made with; exports made before keep working.
- **Export layouts** (a new page, also in Settings): each layout is a JSON file of where everything goes, built from places (the card, ES-DE's folder) and names like `{folder}` and `{stem}`. The editor shows what an export would write as a folder tree, with example games or a collection's first games: choose a folder or file and change where it goes, a system's folder or name, a gamelist tag, a picture size, or leave something out, and the tree follows at once. Faint files are ones none of those games has yet; files that would land on the same name are marked. Problems (a path that doesn't start with a place, pictures with no game's name in them, two parts writing the same file) are shown before you can save. The built-in layouts stay as they are: your change is saved as a new layout in the library (`_library/layouts/`), which can be compared with the one it came from, edited as JSON, saved as a file to share, and imported.
- **BIOS files** (a new page): each system's BIOS and firmware files, audited against libretro's list (System.dat, got from the page or with Get starter DATs) or a BIOS DAT of your own: which you have (found by their hashes, wherever they are and whatever they're called), which are missing, and which have the right name but aren't the right file, the systems you have games for first. Save a report of what's missing. **Gather…** copies those you have into the library's `BIOS/<system>/` folder, with a preview and Undo. The app never downloads BIOS files themselves, only the list.
- Export… carries the systems' BIOS files when ticked, into the layout's BIOS folder (`bios/` on Knulli, `roms/bios/` on ROCKNIX, `MUOS/bios/` on muOS, `BIOS/` beside ES-DE's ROMs on a card).
- **Command line**: `layouts`, `layout show|check|import|write|remove`, `bios`, `bios report`, `bios gather [--dry-run]`, and `export … --layout <id> --place card=E:/ --bios`.
- Plan: Phase 5b's design and notes in `docs/PLAN.md` (D36–D41).
- The page test reads the About page's roadmap by what's still to come, since what's done is folded away.

## 0.5.0 (2026-10-17)

- Roadmap: device profiles for muOS, Knulli, ROCKNIX, and ES-DE on Android or Linux come right after Phase 5, for exporting a collection to a handheld's SD card.
- **Metadata** (a new page): a system's games as its DAT lists them, the ones you have or every one, with what the library holds for each (details, pictures, documents) and those that need a look. A game's panel shows its description, release date, developer, publisher, genres, players and rating, where each came from, its pictures and video, and its documents.
- **Scrape…**: fill in a system's games from ScreenScraper (by the ROMs' hashes, so it knows games by their files), IGDB, TheGamesDB and LaunchBox Games DB (by title), for the games you have or every game in the DAT, so the library has them ahead of the games. Choose the sources and their order, which details and which pictures (box front and back, 3D box, screenshot, title screen, logo, fan art, cartridge or disc, video, manual), a source of its own for any kind of picture, the regions and language, and whether games that have something are filled in, replaced or left. The choices are kept with the library for next time. Everything is kept in the game's folder in the library, found again by its ROMs, not its file name.
- **Needs a look**: a game the sources weren't sure about lists the games it could be; pick the right one, or Identify… it. Scrape… a single game from its panel, and *Clear what was scraped* (your documents stay).
- **Settings › Sources**: the accounts and keys ScreenScraper, IGDB and TheGamesDB need, kept on this computer (never in the library, and passwords never shown again), with Check to try them. ScreenScraper also needs a developer id and password for the app, which it gives on request; Game Repo doesn't have one yet. Identify searches these sources too.
- **Documents** (a new page): every guide, FAQ, manual, map, poster and scan in the library, searched by the words inside them (PDFs with text, text and Markdown files), by kind, system and where they came from. Read one beside the list: PDFs in the system's viewer with page and zoom, pictures, text and Markdown, audio; anything else opens in its own program. A document's title and kind can be changed there.
- **Import documents…**: pick a folder (or files) of guides, manuals or scans; each is paired with the game its name suggests (*Sure*, *Likely* or *No game*), and you can change any pairing by searching a system's games, change its title or kind, or leave it out, before the preview. They go into each game's folder in the library (those with no game into the system's documents), copied (hardlinked on the same drive) or moved, with Undo. **Attach documents…** on a game's panel does the same for one game.
- **Export…** chooses *what it carries*: the details written into ES-DE's gamelists, which pictures and video go into ES-DE's media folder (or beside each game in a plain folder), each game's manual, every document (a plain folder), and a picture size for a handheld's screen (the app makes them smaller itself). Update and Check follow them like the games.
- **Command line**: `games <system>`, `game <id> [--clear | --pick <source> <id>]`, `scrape <system> [--all] [--sources …] [--fields …] [--media …]`, `docs [--search <words>]`, `docs read`, `docs import <folder>`, `sources key <source> --<field> <value>`, `sources check <source>`, and `export … --fields --media --manuals --docs --image-size`.
- The PC games list lines its rows up on the left.

## 0.4.0 (2026-10-17)

- **Disc systems**: PlayStation, PlayStation 2, PSP, Saturn, Sega CD, Dreamcast, PC Engine CD, Neo Geo CD, 3DO, PC-FX, Jaguar CD, CD-i, GameCube, Wii and Xbox, audited against Redump's DATs from cue/bin, gdi and iso sets. A cue sheet that isn't Redump's but names the right tracks counts (*cue differs*), and renaming the set rewrites it to name the new files.
- **CHD, CSO, ZSO and RVZ** are audited as the games they hold: a CHD's tracks as the bins Redump lists, a CSO's or ZSO's ISO, and an RVZ's disc through dolphin-tool (until it's found, RVZ files wait to be checked).
- **Convert…** a game (on the Have list) or a whole platform (at the top of the Audit) to its preferred format (CHD for CD, GD-ROM and DVD systems, RVZ for GameCube and Wii, CSO or ZSO for PSP, ZIP for cartridges), into a folder or in place, and **Extract** back to cue/bin, GDI or ISO, named as Redump names them. Every result is read back and compared with the files it came from before anything is replaced, and Undo puts it all back. CHDs are written by the app itself, byte for byte the data chdman writes, so no tool is needed for them.
- **Settings › Tools** shows where dolphin-tool was found (the app's `tools` folder or the PATH) or lets you choose it; **Settings › Preferred formats** sets what Convert… offers first where a platform has a choice (PSP: CSO, ZSO or CHD).
- **Get starter DATs** now also fetches libretro's copies of Redump's DATs for the disc systems. They list one track of each disc, so import Redump's own DATs for a full check.
- **Command line**: `convert <platform> [--to <format>] [--out <folder>] [--game <name>]… [--dry-run]`, `extract <platform>`, `formats [<platform> <format>]` and `tools [<tool> <path> | --clear <tool>]`.
- **Collections** (a new page): pick games by rules (which systems, the games you have or every game in the DAT, one game per title with your region order, languages, betas, demos and the like left out, a name search, or only the games in DATs of your own), then leave out or add games by hand. A collection can cover several systems, is kept in the library, and follows it as you scan and import.
- **Properties** of a collection: its games, systems and size on disk (by system, and what the games you don't have would add). Give it a **size limit** (a 32 GB or 64 GB card, or any size) and it says whether it fits or by how much it's over; list the games biggest first to choose what to leave out. `collection show` prints the same, and `collection edit <id> --size-limit 64GB` sets one.
- **Save as DATs**: a collection becomes one DAT per system, with each game's ROMs as its DAT lists them, for RomVault, clrmamepro or igir.
- **Export…** a collection to ES-DE (each system in its folder in ES-DE's ROMs folder, a cue/bin game as one folder ES-DE shows as one game, an entry in each system's gamelist and the collection as an ES-DE custom collection) or to a plain folder. Files are hardlinked on the same drive, else copied, and checked, with a preview and Undo. **Update** adds what the collection gained and sets aside what it lost (only files the export put there); **Check** reads the export back against the DATs.
- **Settings › Systems**: add the systems the app doesn't know (a DAT's, a computer's, a handheld's), with their DAT names, folders and file extensions; DATs, folders and files then find them like any other. When a DAT's system isn't recognised, choose any system or add a new one by its name, with no id to type.
- **Command line**: `systems [add|edit|remove]`, `collections`, `collection new|edit|show|dats|delete`, `export <collection> --out <folder> [--to esde|folder] [--esde <folder>]`, `export update|check|forget <export>` and `exports`.
- **PC games** (a new page): put GOG installers (with their `.bin` parts and patches), ZIP and 7z archives, disc images and game folders in an inbox folder (Settings › PC games) and press **Import…**, or pick them. Each is hashed and looked inside: a GOG `goggame` file, the installer's GOG id (with innoextract), a `steam_appid.txt`, or its name and year, and Steam's store or GOG's catalogue is searched for the rest. Review the list (title, year, what each file is, Identify… for any it got wrong, leave any out), see the preview, and each game gets its own folder, `PC/<Title> (<Year>)/` with `install`, `extracted`, `patches`, `extras` and `dlc` and a `game.json` saying what it is, with its artwork. Copied (hardlinked on the same drive) or moved, with Undo. A file already in the library is said to be; a new version of a game you have joins it.
- **A PC game's panel**: its details and artwork, a new title or year (its folder is renamed), the program that starts it, and **Unpack** to play without installing (ZIP and 7z by the app; GOG installers with innoextract, found like dolphin-tool in Settings › Tools).
- **Identify…**: search Steam, GOG and LaunchBox Games DB for a game and pick the right one; its id and details are kept with the game and its cover, banner, hero and logo fetched. **Settings › Sources** sets their order and which are on, and gets LaunchBox's database (searched on this computer, every system).
- **Add to Steam…**: your PC games as non-Steam games in Steam's library, with their covers, banners, heroes and logos in Steam's grid. Your own shortcuts are kept, shortcuts.vdf is backed up first, and it waits until Steam is closed; the app's shortcuts can be taken out again. **Settings › Steam** finds Steam's folder or lets you choose it.
- **Add a game…** (Audit ⋯): a ROM, archive or disc for any other system, copied or moved into a folder with games for it, scanned, and checked against its DAT; one no DAT knows can be identified, and what's found is kept by the file's SHA1.
- **Command line**: `pc [list|show|import|set|unpack|folder|inbox]`, `identify <title>`, `sources`, `launchbox get`, `steam users|preview|write|remove` and `add <file> --platform <id>`.

## 0.2.0 (2026-10-16)

- **Plans**: Phase 2 is designed: organising sets by their DAT names with a preview and Undo, then disc systems and converting to CHD, RVZ and CSO.
- **Organise…** (Audit): sort a platform's set by its DAT in one of three ways: copy it to another folder (hardlinked on the same drive, so it takes no space), rename the files where they are, or move them into a folder for the platform in the library. Choose to keep files as they are, make a ZIP for each game, or unpack them; a preview shows every step, what's in the way and whether there's space, and nothing changes until you press Run. Every file written is read back and checked.
- **Undo**: the message after a change has Undo, and *Settings › History* lists the changes, undoes the newest, and finishes or puts back one that was interrupted (say, by a power cut). Files a change replaces are never deleted: they're set aside in a hidden `.gamerepo-set-aside` folder until you empty it there.

- **TorrentZip**: ZIPs the app writes are byte-for-byte the same as other collectors' TorrentZip tools make, so they match torrents and other people's sets.

- **Watch for changes** (Settings, on by default): while the app is open, files added, changed or removed in your folders with games are read a few seconds later, without a scan. Network drives are still read when you scan.

## 0.1.0 (2026-10-16)

- **Folders with games** (Settings): add the folders your ROMs are in, anywhere on this computer or a network drive, optionally marked with their platform. They're kept in the library; one that's somewhere else on another computer can be pointed there. Nothing in them is ever changed.
- **Scan** (Home or Audit): every file is read once and hashed (CRC32, MD5 and SHA1 together), files inside ZIPs too, and a second scan reads only what's new or changed. ROMs with headers (iNES, FDS, Atari 7800, Lynx, SNES copier) and N64 ROMs in other byte orders are matched as the DATs list them. ZIPs are matched by the checksums they record unless you choose *Unpack and hash every file*; how many files are read at once is a setting too.
- **DAT files** (Settings): import No-Intro, Redump, TOSEC or any Logiqx or ClrMamePro DAT, zipped or not. The platform is worked out from the DAT's name, or asked once and remembered. Each DAT is copied into the library; importing a newer version keeps the older one, and you can choose which is in use.
- **Audit**: for each platform, the games you have, partly have and are missing, with 1G1R completeness, and the files that are named right, misnamed (with the right name), bad dumps, unknown or duplicates, each searchable and with *Show in folder*. A platform can have several DATs; the one you pick stays its DAT.
- **Reports and fixdats**: *Export fixdat* writes what's missing as a DAT; *Copy report* and *Save report* (text or CSV) write the audit out.
- **Get starter DATs**: one click downloads the No-Intro DATs for the cartridge systems from libretro's public copy and imports them for the systems that have none yet. They can be a little behind No-Intro's newest; a newer DAT you import becomes the version in use.
- **Make a DAT from a set**: write a DAT of a folder you've scanned, and import it to audit against.
- **Home** shows a bar per platform, the last scan and what needs attention (folders not found here, files without a DAT or platform).
- **Faster rescans**: scanning folders where nothing changed no longer writes to the index.
- **Roadmap** (About): serving games from the app to Android, Linux and handheld devices on the home network is planned as Phase 9.
- **Command line**: `gamerepo-cli roots`, `scan [--full]`, `dat import|list`, `audit <platform> [--list …] [--fixdat …] [--report txt|csv]` and `make-dat` work on the app's library.

## 0.0.0 (2026-10-16)

The first version of Game Repo: the app itself, with its library and settings. The features come in the next phases; the menu shows what each brings.

- On first start the app asks where your library should go. The library is an ordinary folder: the app adds only a `_library` folder to it, so a folder already holding your games can be used as it is, and nothing in it is changed.
- The app keeps an index of each library on this computer (not in the library), ready for the hundreds of thousands of files a full set has. Settings shows where it is, and Home's Library menu checks it.
- Rename the library (with Undo), open another one, or go back to one opened before from Settings.
- Two looks, Drafting Sheet and Classic, each in light, dark and night themes.
- About shows the version, what's changed, what's coming in each phase, how a library is laid out and the licences.
